## Git e GitHub: conceitos

**Git** é um programa no seu computador que guarda o histórico do projeto. Cada vez que você salva um ponto, ele guarda uma foto de todos os arquivos. Dá para voltar a qualquer foto e ver quem mudou o quê.

**GitHub** é um site que guarda uma cópia do repositório na internet. É por ele que o time compartilha o código.

Os termos que vamos usar:

| Termo | O que é |
|---|---|
| **Repositório** | A pasta do projeto, com todo o histórico |
| **Commit** | Uma foto salva, com uma mensagem ("adiciona prompt do CRIA") |
| **Branch** | Uma linha paralela de trabalho. Você mexe no CRIA sem atrapalhar o ND |
| **Push** | Envia seus commits do computador para o GitHub |
| **Pull** | Traz para o computador o que os outros enviaram |
| **Clone** | Baixa uma cópia do repositório do GitHub |
| **Pull request (PR)** | Um pedido para juntar sua branch na principal (`main`), com revisão |
| **Merge** | A junção em si |
| **Conflito** | Duas pessoas mudaram a mesma linha, e o Git pede que você escolha qual fica |

**O fluxo do time, em resumo**
1. Cada um cria uma branch própria (`cria`, `ped`, `nd`).
2. Trabalha, faz commits e dá push na sua branch.
3. Abre um PR e o time junta na `main`.

Como cada agente fica numa pasta separada, os conflitos devem ser raros.

## O que é um agente de IA

Um **modelo de linguagem** (como o Claude) sozinho só recebe texto e devolve texto. Um **agente** é esse modelo com três coisas em volta:

1. **Instruções (system prompt):** define o papel. "Você é o CRIA, um criador de questões..."
2. **Ferramentas (tools):** funções de código que o modelo pode pedir para executar, como buscar o perfil do aluno ou salvar uma questão. Ele não executa nada sozinho: ele pede, o seu código roda e devolve o resultado.
3. **Um laço (loop):** o modelo pensa, pede uma ferramenta, recebe o resultado, pensa de novo, e repete até terminar.

Um agente, então, é um laço de código ao redor de uma chamada de API. Não tem mágica.

## Como o CRIA se encaixa

Pelo contexto e pelo PDF, o CRIA faz isto:

```
Diagnóstico do PED  →  CRIA  →  questões personalizadas  →  (segue para o ND)
{aluno, competência fraca,      
 score, causa, pré-requisito}
```

**Instruções do CRIA:** criar questões que atacam a lacuna específica, no nível certo, com o contexto do aluno.

**Ferramentas possíveis do CRIA:**
- `buscar_questoes_base`: consulta o banco da Teachy, para não inventar do zero.
- `salvar_questoes`: grava o resultado para o ND e o professor revisarem.

**Regra importante do seu fluxo:** se a lacuna vem de uma matéria anterior (fração, e não equação), o CRIA volta até esse pré-requisito. Isso será parte das instruções.

## Plano de construção

1. **Entrada e saída em formato fixo.** Definimos o diagnóstico que o CRIA recebe e a questão que ele devolve, como JSON. É o contrato com o PED e o ND.

4. **Acrescentar ferramentas e o laço**, quando o resto estiver funcionando.

Começar simples e só depois adicionar ferramentas é o jeito mais seguro de aprender.

## 3. O que é uma chave de API

O modelo de IA (Claude, por exemplo) roda nos servidores de uma empresa, não no seu computador. Para o seu código usá-lo, ele precisa **se identificar**, e a chave de API faz isso. É uma senha longa, tipo `sk-ant-...`.

Ela serve para duas coisas:

- **Cobrar o uso.** Cada chamada gasta tokens, e a conta vai para o dono da chave. É por isso que o seu fluxo de "o professor ativa o dever" evita que um aluno gaste todos os tokens.

## Resumo

O CRIA **não é um serviço separado**. É uma função TypeScript dentro do backend, `createQuestions(input)`, em `backend/src/services/agents/creator.agent.ts`. Ela roda no mesmo processo do servidor Express, não guarda estado e não tem servidor próprio. A única parte "de fora" é o **modelo de linguagem**, que fica na Featherless e é chamado pela internet.

Ele ainda **não está ligado** ao fluxo do diagnóstico. Hoje a função existe, está testada e está no GitHub, mas ninguém a chama.

## Onde fica cada coisa

```
Navegador (frontend)
      │
      ▼
Backend Express (seu servidor)
  ├─ rotas / controllers
  ├─ services (diagnostic-agent.service.ts)  ← orquestra os agentes
  │     ├─ PED   (pedagogical.agent.ts)
  │     └─ CRIA  (creator.agent.ts)          ← função pura, sem banco
  ├─ repositories ──► SQLite
  └─ lib/llm.ts ─────► HTTPS ─► Featherless (modelo Kimi-K2.7-Code)
```

- **Hospedagem:** o código do CRIA vai junto com o backend. O modelo roda na Featherless, e a chave fica na variável `FEATHERLESS_API_KEY`.
- **Custo e tempo:** cada aluno gasta algumas dezenas de milhares de tokens (centavos de dólar) e leva de 10 a 30 segundos.

## Como ele se comunica com os outros agentes

**Os agentes não conversam entre si.** Quem os coordena é o backend (`advanceDiagnostic`), e eles trocam dados pelo banco:

1. O **PED** grava o perfil do aluno (`competency_gaps`, `scores`).
2. O service lê isso e monta um `CreatorInput`.
3. O **CRIA** devolve um `CreatorResult`.
4. O service grava o resultado em `diagnostic_items`.
5. O professor revisa e aprova (`diagnostic_students.approved`).

Isso é o que ainda falta: o passo 2 e o passo 4 (as colunas e o ajuste da transação que você e o Lucas estão resolvendo).

## O que acontece dentro do CRIA

1. **Valida a entrada** (nota de 1 a 100, campos obrigatórios).
2. **Escolhe o foco, em código e sem IA.** Se a causa é `tecnica`, existe pré-requisito e a nota é menor que 60, ele volta ao pré-requisito. Senão, trabalha a competência. Essa regra é determinística de propósito, para não depender do humor do modelo.
3. **Primeira chamada ao modelo:** envia as instruções (system prompt) e o diagnóstico, e pede JSON com as questões.
4. **Lê o JSON.** Aceita resposta cercada por texto ou por ```.
5. **Checagem de gabaritos, com uma segunda chamada.** Ela recebe as questões **sem o gabarito** e escreve só a conta que resolve cada uma. O código executa essa conta (só números e funções de `Math` são aceitos) e compara com o gabarito.
6. **Se algum gabarito divergir**, gera de novo, no máximo duas tentativas, e fica com a melhor.

**Importante, sem exagero:** isso é um *pipeline* de duas chamadas ao modelo, não um agente autônomo com ferramentas e laço de decisão. Ele não decide sozinho o que fazer em seguida. Para o hackathon isso é uma vantagem: é previsível, testável e rápido de explicar.

## Formato de entrada (`CreatorInput`)

```json
{
  "studentName": "Ana",
  "subject": "Matemática",
  "competency": "equações do 1º grau",
  "score": 40,
  "reading": "tecnica",
  "prerequisite": "operações com frações",
  "context": "Mora em Manaus; gosta de futebol"
}
```

`prerequisite` vem do PED e `context` é do professor. Os dois são opcionais.

## Formato de saída (`CreatorResult`)

```json
{
  "focus": { "topic": "operações com frações", "reason": "A dificuldade em ... vem de uma base fraca em ..." },
  "questions": [
    {
      "statement": "Durante um treino em Manaus, 2/3 do time tomaram água e 1/6 isotônico. Qual fração consumiu algum líquido?",
      "kind": "multipla_escolha",
      "options": ["A) 1/2", "B) 3/9", "C) 5/6", "D) 1/6"],
      "answerKey": "C",
      "resolution": "2/3 = 4/6. Então 4/6 + 1/6 = 5/6.",
      "difficulty": "facil",
      "check": { "status": "ok", "computed": 0.833 }
    }
  ]
}
```

`check.status` é `ok`, `divergente` (traz `computed` e `expected`) ou `nao_verificavel`. O modelo responde com chaves em português, e o código as traduz para esses campos em inglês.
